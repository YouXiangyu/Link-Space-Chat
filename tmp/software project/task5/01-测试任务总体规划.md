#### 2.1.3 项目概述（30秒）
- **项目定位**: 轻量级，零认证，广适配的即时消息平台
- **核心特点**:
  - 跨网络环境支持（局域网和公网）
  - 无需注册，通过链接快速加入
  - 保护隐私，安全性强
- **讲解要点**: 可能大家还是对我们的软件没有概念，接下来我会和微信对比

#### 2.1.4 对比微信（30秒）
- **架构对比**:
  - **微信的网络架构**：我们发送的信息，会先传到微信服务器，然后再发送到客户
  - **我们的架构**：可以将我们手头的电脑，变成服务器，发起整个聊天网络
- **数据安全对比**:
  - **微信**：所有数据都是经过服务器的，有泄露风险
  - **我们的软件**：服务器和客户端都是自己的设备，就极大的保证了数据安全
  - **网络适配优势**：因为独特的服务器网络位置，我们就能实现在本地（localhost访问），局域网（ip地址：端口访问），公网（通过Ngrok服务）
- **讲解要点**: 展示核心能力与区别，更直观理解项目定位，与微信的差异

#### 2.1.5 技术架构（40秒）
- **后端技术栈**:
  - Node.js + Express.js（HTTP服务器）
  - Socket.IO（包装了复杂的通讯协议）
  - SQLite（数据库）
  - Ngrok（公网暴露）
- **前端技术栈**:
  - HTML5 + CSS3 + JavaScript
  - ES6 Modules模块化架构
- **系统规划**:
  - 前后端分离
  - 事件驱动
  - 服务层设计

#### 2.1.6 核心模块设计（40秒）
- **数据库模块**:
  - 房间管理
  - 消息储存
  - 投票功能
- **Socket.IO事件处理**:
  - joinRoom: 加入房间
  - chatMessage: 发送消息
  - leaveRoom: 离开房间
  - updateRoom: 更新房间信息
- **服务层**:
  - RoomState: 房间状态管理（内存）
  - RateLimiter: 消息频率限制
  - MessageService: 消息处理服务
  - HealthReporter: 健康检查服务

**注意**: 核心模块仅展示功能，不展示细节。设计文档引用在Demo部分展示。

### 4.4 Debug细节分享（1分钟）

#### 4.4.1 Bug案例：历史记录加载问题
- **问题描述**: 历史消息加载异常，投票数据缺失
- **PIE模型分析**:
  - Execution（执行）：异步循环执行过程中发生错误
  - Infection（感染）：错误导致投票数据未正确加载到消息对象中
  - Propagation（传播）：错误传播到前端，导致投票消息显示异常
- **调试流程**:
  1. 复现（Reproduce）：重现bug场景（加载包含投票的历史消息）
  2. 定位（Locate）：确定bug的位置（joinRoom.js第124-141行的循环加载逻辑）
  3. 理解（Understand）：理解bug的原因（异步循环错误处理不足，数据库查询失败未捕获）
  4. 修复（Fix）：使用Promise.all并行加载，添加try-catch错误处理
  5. 验证（Verify）：验证修复是否有效（重新加载历史消息，投票数据正常显示）

### 4.5 我们所做的维护（1分钟）
- **维护类型**:
  - 改正性维护（Corrective）：修复发现的错误（分析git记录）
  - 适应性维护（Adaptive）：适应环境变化（分析git记录）
  - 完善性维护（Perfective）：改进功能和性能（分析git记录）
  - 预防性维护（Preventive）：预防未来问题（分析git记录）
- **Git记录分析**: 统计各种维护类型的次数和具体案例
  - 改正性维护：fix: 开头的提交（如：fix:修复小窗口下ui显示异常的问题、fix:无法加载历史消息）
  - 适应性维护：chore: 开头的环境相关提交（如：chore:删除了不再使用的数据库文件）
  - 完善性维护：feat: 开头的功能提交（如：feat: 实现投票功能、feat:ui适配功能开发）
  - 预防性维护：docs:、refactor: 开头的提交（如：docs：readme重写、refactor: 解耦，删除重复代码）
