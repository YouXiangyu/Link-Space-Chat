## 二、需求来源 (Task2 - URS) (5-7分钟)

### 2.1 需求收集方法
- **用户调研**: 24份有效问卷
- **目标用户**: 学生（特别是计算机/IT相关专业）和年轻职场人士
- **核心痛点**:
  - 传统IM软件"先加好友再沟通"流程繁琐
  - 不愿暴露私人社交媒体账号
  - 临时群聊难以删除

### 2.2 系统功能概述
基于用户调研，系统需要满足以下核心功能：

#### 2.2.1 房间管理功能 (REQ-1.x)
- **REQ-1.1**: 一键创建房间
  - 主机用户通过简单命令启动服务
  - 自动生成访问链接
- **REQ-1.2**: 生成访问链接
  - 自动生成局域网链接
  - 可选生成公网链接（通过Ngrok）
- **REQ-1.3**: 自动数据删除
  - 最后一个用户离开时自动清空聊天记录
  - 确保临时性和隐私保护

#### 2.2.2 消息功能 (REQ-2.x)
- **REQ-2.1**: 文本消息
  - 实时发送和接收文本消息
- **REQ-2.2**: 表情符号支持
  - 支持标准Emoji输入和渲染
- **REQ-2.3 & 2.4**: 图片和文件分享
  - 图片内联显示
  - 文件提供下载链接
  - 单文件限制5MB
- **REQ-2.5**: Markdown支持
  - 支持基本Markdown语法（粗体、斜体、代码块）

#### 2.2.3 用户交互功能 (REQ-3.x)
- **REQ-3.1**: 临时昵称
  - 首次进入房间必须设置昵称
  - 昵称在房间内唯一
  - 长度限制：1-20字符
- **REQ-3.2**: 在线用户列表
  - 实时显示房间内所有在线用户
- **REQ-3.3**: 加载历史消息
  - 新用户加入时自动加载最近20条消息

### 2.3 非功能需求
- **性能要求**:
  - 进入房间时间：≤3秒
  - 消息延迟：≤1秒
  - 首次使用到发送第一条消息：≤60秒
- **安全要求**:
  - 不收集个人身份信息（PII）
  - 加密传输（HTTPS/WSS）
  - 临时数据存储
- **可用性要求**:
  - 依赖主机用户设备在线
  - 支持至少10个并发用户

### 2.4 系统约束
- **软件约束**:
  - 主机：Node.js v16+
  - 参与者：现代浏览器（支持WebSocket）
- **硬件约束**:
  - 主机：可运行Node.js的PC或服务器
  - 参与者：支持现代浏览器的设备

### 3.2 功能建模 - 数据流图 (DFD) (6-8分钟)

#### 3.2.1 上下文图 (0级 DFD)
**图表**: `DFD-0.svg`

**讲解要点**:
- 将整个系统视为单一过程
- **外部实体**:
  - `Host User`（主机用户/管理员）
  - `Participant User`（参与用户）
  - `Health Probe / Monitor`（健康探测/监控服务）
  - `Ngrok Tunnel Service`（Ngrok穿透服务）
- **主要数据流**:
  - 主机用户 ↔ 系统：启动命令、访问链接
  - 参与用户 ↔ 系统：消息、房间操作
  - 系统 ↔ Ngrok：隧道配置、公网URL

**关键信息**:
- 展示了系统的边界和与外部环境的交互
- 明确了系统的输入输出

- **数据存储**:

  - `D2 房间与成员`：房间和成员关系
  - `D3 消息`：消息记录

**关键信息**:

### 3.3 数据建模 - 实体关系图 (E-R图) (4-5分钟)
**图表**: `1.ER-1svg.svg`

**讲解要点**:
- **核心实体**:
  1. **用户 (User)**
     - 属性：id、昵称、密码哈希
     - 说明：系统使用者
  2. **房间 (Room)**
     - 属性：id、名称、描述等
     - 说明：用户互动的聊天室
  3. **消息 (Message)**
     - 属性：id、房间ID、昵称、内容、创建时间等
     - 说明：用户在房间内发送的消息
  4. **房间成员关系 (Room_Membership)**
     - 关联实体：连接用户和房间
     - 说明：多对多关系
  5. **投票 (Poll)**
     - 属性：id、消息ID等
     - 说明：用户在房间内创建的投票
  6. **投票选项 (Poll_Option)**
     - 属性：id、投票ID、选项文本
     - 说明：投票中的单个选项
  7. **表决 (Vote)**
     - 属性：id、选项ID、用户ID、创建时间
     - 说明：用户对投票选项的投票

- **关系说明**:
  - 用户 ↔ 房间：多对多（通过Room_Membership）
  - 用户 → 房间：一对多（创建关系）
  - 消息 → 房间：多对一
  - 消息 → 用户：多对一
  - 投票 → 房间：多对一
  - 投票 → 投票选项：一对多
  - 投票选项 → 表决：一对多

**关键信息**:
- 为数据库设计提供了蓝图
- 明确了数据实体之间的关系
- 支持后续的数据库实现

---

### 3.4 行为建模 - 状态转换图 (STD) (4-5分钟)
**图表**: `5. State Transition Diagram.svg`

**讲解要点**:
- **状态说明**:
  1. **开始 (Start)**: 会话的初始入口点
  2. **在大厅 (InLobby)**: 客户端连接后、加入房间前的状态
  3. **加入中 (Joining)**: 系统处理加入请求的过渡状态
  4. **聊天中 (Chatting)**: 用户成功进入房间，可发送/接收消息
  5. **重连中 (Reconnecting)**: 网络连接丢失时的状态
  6. **已断开 (Disconnected)**: 用户登出或重连失败
  7. **结束 (End)**: 会话的最终终止点

- **状态转换**:
  - `提交加入 (submit_join)`: 在大厅 → 加入中
  - `加入成功 (join_success)`: 加入中 → 聊天中
  - `网络丢失 (network_lost)`: 聊天中 → 重连中
  - `重连成功 (reconnect_success)`: 重连中 → 在大厅
  - `重连失败 (reconnect_failed)`: 重连中 → 已断开
  - `登出 (logout)`: 聊天中 → 已断开

**关键信息**:
- 描述了客户端连接的生命周期
- 明确了状态转换的触发条件
- 为前端状态管理提供了指导

## 五、Q&A 环节 (3-5分钟)

### 可能的问题准备
1. **为什么选择结构化分析方法而不是面向对象方法？**
   - 结构化方法更适合数据流驱动的系统
   - DFD能清晰展示消息处理的流程
   - 对于实时通信系统，数据流分析更直观

2. **E-R图中的实体是否都已在系统中实现？**
   - 部分实体已实现（Room、Message）
   - 部分实体为未来功能预留（Poll、Vote）

3. **状态转换图如何指导前端开发？**
   - 明确了前端需要管理的状态
   - 定义了状态转换的触发条件
   - 为错误处理提供了指导
